# Bug Report

Severity: **Critical** (breaks a core feature or produces wrong data with no workaround), **High** (broken feature with workaround, or silent data loss), **Medium** (incorrect display, confusing UX), **Low** (cosmetic/dead code).

All bugs below were found by static code reading (no app was run); line numbers refer to the files as read during this audit.

---

## CRITICAL

### BUG-01: Compliance Health Score always shows "Healthy" (100%)
**File**: `src/services/complianceScore.ts`, `getGroupComplianceScore()` / `calculateFromItems()`

The primary query selects `title, dueDate, status, priority, risk_level, required_documents, companyId` — camelCase `dueDate`/`companyId`, which are NULL for every normally-created compliance item (the app writes `due_date`/`company_id`). The query does **not** also select `due_date`. In `calculateFromItems`, `dueDateStr = item.dueDate || item.due_date` evaluates to `undefined` for every item (neither key has a value), so `if (!dueDateStr) return;` skips every item in the scoring loop. `score` never decreases from its initial 100, and `items.length > 0` so the "no items" fallback path isn't hit either.

**Impact**: The dashboard's headline compliance health indicator is **always green/"Healthy"** regardless of actual overdue or at-risk items — directly undermines the product's core value proposition (compliance risk visibility).

**Fix**: query `due_date, company_id` (snake_case) as primary fields, or `coalesce` both in the select via two separate queries as the existing fallback path already does correctly (the fallback path, triggered only on a query *error*, is actually correct — but the primary path doesn't error, so the fallback never runs).

### BUG-02: Compliance items generated by the engine are invisible everywhere
**Files**: `src/services/complianceEngine.ts` (`generateComplianceForCompany`), `src/pages/Companies.tsx`, `src/components/companies/ComplianceSetupWizard.tsx`

`ComplianceEngine.generateComplianceForCompany()` inserts rows shaped `{ companyId, dueDate, owner_id, title, type, category, status, priority, risk_level, required_documents }` — i.e. camelCase `companyId`/`dueDate`. Every consumer (`Compliance.tsx`, `complianceActions.ts`/Today's Actions, `CompanyProfile.tsx` compliance tab, `Dashboard.tsx`, `ComplianceReport.tsx`) queries `company_id`/`due_date`. These generated rows therefore never appear anywhere in the UI.

Additionally, at initial company creation (`Companies.tsx`), `data.legalEntityType` is `undefined` (insert was snake_case-only), so `typeMatch` is always false and `matchedTemplates` is empty — **zero items generated** at this stage, silently (try/catch swallows, no error surfaced).

**Impact**: The flagship "Compliance Automation" feature produces no user-visible output through any normal flow. New companies appear to have "no compliance obligations," which is both factually wrong and dangerous (users may believe they have nothing due).

**Fix**: standardize `ComplianceEngine` inserts on `company_id`/`due_date` (snake_case) and pass a normalized company object (with `legal_entity_type`, `incorporation_date`, `financial_year_end` always populated) into both `generateComplianceForCompany` and `getPreview`.

### BUG-03: "New Compliance Entry" creation is broken in default view
**File**: `src/pages/Compliance.tsx`, create/edit modal

The "Selected Entity" `<select>` is bound to `formData.companyId` (`value={formData.companyId}`, `onChange={... companyId: e.target.value}`) — but `initialFormState` (and `handleSubmit`'s payload) use `company_id`. The dropdown is therefore always blank and effectively read-only/non-functional for changing the company.

- In "Single Entity" view, `handleAddClick` pre-fills `formData.company_id` with the current company — submission may succeed, but the user cannot pick a different company.
- In "All Entities" (default) view, `formData.company_id` defaults to `''`. Submitting inserts `company_id: ''` into a `uuid` FK column — Postgres will reject this (`invalid input syntax for type uuid`), surfaced via `setError(err.message)`.

**Impact**: Creating a new compliance item from the main Compliance page (the default/most discoverable entry point) fails for most users.

**Fix**: bind the select to `formData.company_id` / `e.target.value` consistently (same root-cause class as BUG-04, Structure.tsx).

### BUG-04: Group Structure relationship creation is broken (carried over from prior audit pass)
**File**: `src/pages/Structure.tsx`

The relationship-creation form state (`relForm.parentCompanyId`/`childCompanyId`, camelCase) does not match the `company_relationships` insert payload's expected snake_case (`parent_company_id`/`child_company_id`). Same class of bug as BUG-03 — confirms this is a **systemic pattern**, not an isolated mistake.

**Impact**: Users cannot record parent/subsidiary ownership relationships via the UI — a core feature of a "HoldCo OS" product.

## HIGH

### BUG-05: `company_tax_profiles` column-name mismatch (`is_*` prefix)
**Files**: `supabase/migrations/20240502_compliance_engine.sql` (defines `is_vat_registered`, `is_paye_registered`, `is_uif_registered`), vs. `src/pages/Companies.tsx`, `src/components/companies/ComplianceSetupWizard.tsx`, `src/services/complianceEngine.ts` (all read/write `vat_registered`/`paye_registered`/`uif_registered`, no `is_` prefix).

Confirmed via grep: no migration ever creates bare `vat_registered`/`paye_registered`/`uif_registered`. Inserts/selects referencing these columns should fail with "column does not exist." If caught silently (most call sites wrap in try/catch), `taxProfile` would never load real values, defaulting to all-false — compounding BUG-02's flag-based template filtering (PAYE/UIF items never generated even when the company IS registered).

**Fix**: rename either the DB columns or the app references so they match — recommend matching the DB (`is_vat_registered` etc.) since changing a migration that's already applied is riskier than updating ~3 call sites.

### BUG-06: Activity log entries silently fail for camelCase-param callers
**File**: `src/services/activityLogService.ts` (`logActivity({ action_type, ... })`, `action_type` is NOT NULL)

Multiple call sites pass `actionType`/`companyId` (camelCase) instead of `action_type`/`company_id`:
- `complianceEngine.ts`: `actionType: 'compliance_generated'`, `companyId: company.id`
- `complianceScore.ts`: `actionType: 'score_calculated'`

Since `params.action_type` is `undefined` and the column is `NOT NULL`, the insert throws; `activityLogService.ts` catches and only `console.error`s. Users never see "Generated N compliance items" or "Compliance health score recalculated" in their activity feed, with no indication anything went wrong.

**Fix**: fix the two call sites to use `action_type`/`company_id`. Consider also making `logActivity` itself defensively accept either casing (a stopgap) while the real fixes land — but prefer fixing call sites per REFACTOR_PLAN.md's "pick one convention" approach.

### BUG-07: `src/lib/activity.ts` is a second, incompatible activity logger
**File**: `src/lib/activity.ts` vs. `src/services/activityLogService.ts`

Two parallel implementations exist:
- `activityLogService.ts`: `logActivity({ action_type: ActionType (17 values), description, company_id?, compliance_id?, document_id?, metadata? })` — canonical, matches `activity_log` schema.
- `lib/activity.ts`: `logActivity({ eventType: 'create'|'update'|'delete'|'upload'|'login', entityType: 'company'|'compliance'|'document'|'finance'|'user', entityId: string, description, companyId? })` — different param names AND a different, smaller `ActivityType`/`EntityType` union.

Per prior-session findings, `Finance.tsx` imports `lib/activity.ts`'s `logActivity` but calls it with **the other** signature's shape (`action_type: 'finance_created'`/`'finance_updated'`/`'finance_deleted'`, `description`, `company_id`) — values that match neither union, and keys (`action_type`) that don't match `lib/activity.ts`'s expected `eventType`. `params.eventType` is `undefined` at runtime → inserted `action_type`/`event_type`... whichever column `lib/activity.ts` actually writes... would be `undefined`/NULL.

**Impact**: All finance create/update/delete operations likely fail to log activity (silently or as a TS error depending on strictness), and the codebase has two divergent "ActivityType" vocabularies that will keep causing this class of bug as new features are added.

**Fix**: delete `src/lib/activity.ts`, migrate `Finance.tsx` to `ActivityLogService.logActivity()` with correct snake_case params and a valid `ActionType` (add `'finance_created'|'finance_updated'|'finance_deleted'` to the `ActionType` union in `activityLogService.ts`).

### BUG-08: Deletions consistently mislabeled as "updated" in activity log
**Files**: `src/pages/Companies.tsx` (`confirmDelete`), `src/pages/Compliance.tsx` (`confirmDelete`), `src/pages/CompanyProfile.tsx` (`logCompanyActivity` helper used for shareholder/director/beneficial-owner deletes)

At least 3+ confirmed instances of `action_type: 'company_updated'` or `'compliance_updated'` being logged for what the `description` text says is a **deletion**. In `CompanyProfile.tsx`, the shared `logCompanyActivity` helper maps both `'update'` and `'delete'` event types to `'company_updated'` — a single root cause affecting all ownership-entity (shareholder/director/beneficial-owner) delete operations.

**Impact**: Audit trail (a compliance-relevant feature for a holding-company product) misrepresents deletions as updates — undermines the trustworthiness of the activity log for its intended governance purpose.

**Fix**: add `'company_deleted'`, `'compliance_deleted'`, `'shareholder_removed'`, `'director_removed'`, `'beneficial_owner_removed'` (or similar) to `ActionType`, and pass the correct value at each delete call site / extend `logCompanyActivity`'s mapping to a 3-way switch.

## MEDIUM

### BUG-09: Compliance Overview tab always shows "N/A" for due dates
**File**: `src/pages/Compliance.tsx`, "Urgent Compliance Items" (Overview tab, ~line 784)

`{formatDate(item.dueDate)}` — `item` is typed as `ComplianceWithCompany` with `due_date` (snake_case) only; `item.dueDate` is `undefined`, so `formatDate` returns `'N/A'`. The Register tab's `renderRegister()` correctly uses `item.due_date` — only the Overview tab is affected.

**Fix**: change to `item.due_date`.

### BUG-10: Header notification bell over-triggers "Missing Documents"
**File**: `src/components/Header.tsx`, notification fetch / `isMissingDocs` check (~line 90)

`isMissingDocs = item.status !== 'Completed' && item.required_documents?.length > 0 && !item.linkedDocumentId` — checks camelCase `linkedDocumentId`, which is never populated (Compliance.tsx writes `linked_document_id`). For any non-completed item with `required_documents`, `!item.linkedDocumentId` is always true, so the badge fires even when a document **has** been linked via `linked_document_id`.

**Fix**: check `item.linked_document_id`.

### BUG-11: Global search can't find companies by registration number
**File**: `src/components/Header.tsx`, global search (~lines 116-144, 242)

`.or('name.ilike...,registrationNumber.ilike...')` — `registrationNumber` is the camelCase compat column on `companies`, populated only via the one-time backfill for pre-migration rows; NULL for every company created since. Search by registration number returns nothing for any company created after the alignment migration. Result rendering (`c.registrationNumber`) also shows blank for these companies.

**Fix**: search/display `registration_number`.

### BUG-12: Header notification/search queries use inconsistent FK join names
**File**: `src/components/Header.tsx` (notification fetch ~line 77, search ~lines 130-131) vs. `src/pages/Compliance.tsx`/`complianceActions.ts` (`companies!company_id`)

Header uses `companies!companyId` (camelCase FK reference) while the rest of the app uses `companies!company_id`. Both FK columns/constraints exist (per the alignment migrations), so this may not error, but for normally-created rows (where only `company_id` is populated), the `companies!companyId` join returns a NULL company name.

**Fix**: standardize all joins on `companies!company_id`.

### BUG-13: Compliance modal document-link preview never renders file info
**File**: `src/pages/Compliance.tsx`, document-linking preview (~lines 1117-1153)

References `linkedDoc.fileType`/`linkedDoc.fileUrl` (camelCase) — `Document`/Documents.tsx use `file_type`/`file_url`. Preview always falls back to generic "FILE" label; the view/download button (`linkedDoc.fileUrl && ...`) never renders.

### BUG-14: `company_tax_profiles` may never populate `taxProfile` state correctly
**File**: `src/components/companies/ComplianceSetupWizard.tsx` (lines 65-83)

Fetches `company_tax_profiles` via `.select('*')...maybeSingle()` then assigns `data.vat_registered`, `data.paye_registered`, `data.uif_registered`, `data.has_employees` directly to `taxProfile` state. If the actual DB columns are `is_vat_registered` etc. (BUG-05), `data.vat_registered` is `undefined`, and `taxProfile` resets to all-false on every load — meaning step 2 of the wizard ("Tax Questions") would never reflect previously-saved answers.

**Fix**: tied to BUG-05's resolution.
